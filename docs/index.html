Multiagent Framework — White Paper

A config-driven architecture for building production AI systems — where YAML replaces TypeScript for every domain decision.

01 Config-Driven Philosophy

Introduction

Most AI frameworks couple architecture to code. Adding a new agent, swapping a pattern, or connecting a domain knowledge source requires editing TypeScript, recompiling, and redeploying. This framework inverts that relationship: the YAML config file is the application.

Definition

A config-driven framework declares the complete runtime behavior — agents, patterns, context, memory, graph topology — in structured data files, with the engine remaining domain-agnostic TypeScript that interprets those declarations.

What

Every structural decision lives in YAML. TypeScript contains only general-purpose machinery — parsers, executors, validators.

Why

Domain experts extend the system without writing code. Reviews are YAML diffs, not interleaved logic diffs.

When

Multiple domains sharing one codebase without coupling — healthcare, legal, finance on the same engine.

Where

At every layer: agent identity, orchestration pattern, context templates, graph topology, knowledge nodes and edges.

In This Repository

name: Hospital Prescription Workflow
pattern: supervisor
goal: "Review and approve Dr. Chen's prescription for patient Jones"
llm:
  model: claude-sonnet-4-6
agents:
  - id: doctor
    role: Doctor
    promptFile: prompts/doctor.md
    contextRole: doctor       # links to templates/context/doctor.context.yml
  - id: supervisor
    isSupervisor: true
    workers: [doctor, pharmacist]
supervisorConfig:
  supervisor: supervisor
  input: "{{goal}}"
  maxTurns: 8

Code Invocation

import { loadConfig } from "./src/config.js";
import { runApp }    from "./src/orchestrator.js";

const config = loadConfig("configs/hospital-prescription.yaml");
const ctx    = await runApp(config, path.dirname(configPath));
// That's it. No TypeScript changes per domain.
✓ Zero-code extension

To add a new domain (e.g. legal review), copy a config file, change prompts and vars. No TypeScript changes required.

02 Prompt Engineering (Layer 1)

Definition

The practice of crafting model instructions — system prompts, role definitions, output format guidance — to reliably elicit desired behavior from a language model.

What

System prompts, inline instructions, role definitions, output format constraints, and few-shot examples.

Why

The model has no external memory. Every behavioral constraint must arrive within the context window.

When

Before any other layer — prompts are resolved first; context injection and tool results sit below them in message structure.

Where

agents[].prompt (inline) or agents[].promptFile (path relative to config). Both support {{vars}} interpolation.

Config Example

agents:
  - id: doctor
    promptFile: prompts/doctor.md  # relative to config directory
  - id: pharmacist
    prompt: |
      You are a licensed pharmacist. Review the prescription for
      drug interactions and formulary compliance.
      Respond with: APPROVED, FLAGGED, or REJECTED with rationale.

03 Sequential Pattern

Definition

A fixed, ordered list of agent steps where each step's output is stored as a named variable and referenced as the next step's input via template strings.

What

Step A → Step B → Step C. Each step reads from vars and writes to vars.

Why

Simple assembly lines — summarize → translate → format — where each transformation depends exactly on the previous result.

When

Tasks with a clear linear decomposition and no branching or concurrency.

Where

pattern: sequential + workflow.steps[]. Checkpoint/resume supported per step.

pattern: sequential
workflow:
  steps:
    - agent: researcher
      input:  "{{goal}}"
      output: raw_research
    - agent: writer
      input:  "Summarize this research: {{raw_research}}"
      output: draft
    - agent: editor
      input:  "Polish this draft: {{draft}}"
      output: final_output

04 Supervisor Pattern

Definition

A single orchestrating agent dynamically delegates tasks to a roster of worker agents, synthesizing their responses until the goal is met or the turn budget is exhausted.

What

One supervisor LLM decides which worker to call next, interprets results, and either delegates again or declares completion.

Why

Dynamic delegation — the supervisor decides at runtime which specialist to consult, not a fixed sequence.

When

Complex goals requiring multiple experts in an order that depends on intermediate results.

Where

pattern: supervisor + supervisorConfig:. Workers listed under supervisorConfig.workers.

pattern: supervisor
supervisorConfig:
  supervisor: pharmacy_supervisor
  workers:    [doctor, pharmacist, drug_checker]
  input:      "{{goal}}"
  maxTurns:   10
  tokenBudget: 50000
  contextWindowTurns: 6   # older turns collapsed to summary

agents:
  - id: pharmacy_supervisor
    isSupervisor: true
    description: "Coordinates prescription review workflow"
    promptFile: prompts/supervisor.md
  - id: doctor
    description: "Licensed physician, reviews clinical appropriateness"

05 Parallel Pattern

Definition

Fans a single input to N agents simultaneously, then funnels all results to a single aggregator agent that synthesizes a final answer.

What

N agents run concurrently with the same input. Aggregator receives all N outputs as a combined prompt.

Why

Reduces wall-clock time for independent analyses; enables multi-perspective synthesis.

When

Reviewing a document from legal, technical, and UX angles simultaneously.

Where

pattern: parallel + parallel: block.

pattern: parallel
parallel:
  agents:     [legal_reviewer, technical_reviewer, ux_reviewer]
  input:      "{{goal}}"
  aggregator: synthesis_agent
  output:     final_report

06 Hierarchical Pattern

Definition

Nests multiple supervisor layers — a root supervisor manages mid-level supervisors, each of which manages their own worker teams — forming a tree-shaped delegation structure.

pattern: hierarchical
hierarchical:
  rootSupervisor: cto_agent
  input: "{{goal}}"
  maxTurns: 20

agents:
  - id: cto_agent
    team: [backend_lead, frontend_lead]
  - id: backend_lead
    team: [api_engineer, db_engineer]
  - id: frontend_lead
    team: [react_engineer]

07 Plan-Execute Pattern

Definition

A planner agent emits a dynamic step list at runtime. That plan is schema-validated before execution, and each step references an agent from an explicit allow-list — preventing arbitrary execution through plan injection.

⚠ Security note

The executorAgents allow-list is validated at schema ingress. A compromised planner cannot invoke agents outside this list.

pattern: plan_execute
planExecute:
  planner:        orchestrator_agent
  executorAgents: [web_searcher, summarizer, formatter]
  input:          "{{goal}}"
  maxSteps:       8

08 Context Engineering (Layer 2)

Introduction

Once prompts are in place, the next engineering challenge is ensuring each agent has the right domain data at the right time — without hardcoding that data into prompts. Context Engineering externalizes assembly into typed, role-aware templates.

Definition

The practice of designing, assembling, and injecting structured contextual information into a model's context window on a per-agent, per-role basis — using token budgets and priority chains to manage finite context space.

What

Role-specific YAML templates define which fields each agent role needs — type, PHI sensitivity, TTL, and cache promotion policy.

Why

Avoids bloating every prompt with all possible context; ensures each agent receives only relevant data.

When

Any multi-role system where agents have meaningfully different information needs.

Where

contextManager: in config + templates/context/*.context.yml + contextRole: on each agent.

Context Template

# templates/context/doctor.context.yml
role: doctor
fields:
  patientName:
    type: DomainContext
    ttl: 600
    requirement: REQUIRED
    phi: true
  currentMedications:
    type: DomainContext
    ttl: 300
    requirement: OPTIONAL
    phi: true
    evict_on: [medication_update]
  hospitalProtocol:
    type: SystemContext
    ttl: 3600
    requirement: REQUIRED
    phi: false
    promote: always
  requestTimestamp:
    type: TemporalContext
    ttl: 60

Config (no TypeScript change)

contextManager:
  templateDir: templates/context
  allowPhi: false              # PHI fields → [REDACTED-PHI]
  tokenBudgetSplit:
    system:       0.10
    domain:       0.35
    user:         0.20
    conversation: 0.35

agents:
  - id: doctor_agent
    contextRole: doctor        # loads doctor.context.yml automatically
    promptFile:  prompts/doctor.md

Supported Context Types

TypePurposeAuto-resolved
UserContextEnd-user profile, preferencesFrom vars
DomainContextDomain entity data (patient, order)From vars
SystemContextProtocol, model identity, configFallback constants
ConversationContextPrior turns, session stateFrom vars
RetrievalContextRAG-retrieved documentsVia retrieval store
TemporalContextTimestamps, dateAuto (current time)
GraphContextKnowledge graph traversal resultVia GraphStore path

09 Memory Management

Definition

A warm-tier LRU cache that stores frequently accessed context field values — keyed by tenantId:entityId:fieldName — so repeated agent calls retrieve cached values without re-fetching, while respecting PHI hard-blocks.

What

In-memory LRU store. Entity-scoped keys. Values have TTL and access-count thresholds for promotion.

Why

Context assembly is called on every agent invocation. Without caching, the same patient record might be re-derived dozens of times per run.

When

Multi-turn workflows where the same entity appears across many agent calls.

Where

memoryManager: block in config. Each field's promote policy controls warm-tier entry.

memoryManager:
  warmTierMaxEntries:   1000
  defaultTtlSeconds:    300
  accessCountThreshold: 3      # promote after 3 accesses (for promote: access_count)

PHI fields (phi: true) are never promoted to the warm tier, regardless of the promote policy.

10 Dynamic Context Updates (ContextEventBus)

Definition

An event-driven cache invalidation bus that evicts warm-tier entries when domain events (room changes, discharges, medication updates) occur, ensuring agents always receive current data rather than stale cached values.

# In doctor.context.yml
fields:
  assignedRoom:
    type: DomainContext
    ttl: 300
    evict_on: [room_change, transfer, discharge]
  treatingPhysician:
    type: DomainContext
    ttl: 600
    evict_on: [doctor_reassignment]
// Publish a domain event — no config change needed:
eventBus.publish({
  type:      "room_change",
  tenantId:  "hospital-a",
  patientId: "patient_jones",
});
// All warm-tier entries for assignedRoom evicted for patient_jones

11 PHI Gating & Compliance

Definition

A per-field compliance gate preventing Protected Health Information from entering the warm-tier cache or being shown in injected context, replacing the value with [REDACTED-PHI] when allowPhi: false.

contextManager:
  allowPhi: false         # globally redact all phi:true fields

# In doctor.context.yml:
fields:
  patientDOB:
    type: DomainContext
    phi: true             # never cached; redacted if allowPhi: false
  diagnosisCode:
    type: DomainContext
    phi: true
⚠ HIPAA compliance

Set allowPhi: false for all agents that do not have a clinical need for raw PHI. The framework enforces this at assembly time — there is no way for a phi: true field to reach the warm tier.

12 Graph Engineering (Layer 3)

Introduction

Context Engineering solved what data each agent receives. Graph Engineering addresses how agents relate to each other and how domain entities relate to each other — both modeled as explicit graphs declared in config.

Definition

The practice of expressing AI workflow topology (Jobs, Arrows, State) and domain entity relationships (Knowledge Graph) as explicit directed graphs in configuration — enabling the runtime to execute, traverse, and reason over structured relationships without code changes.

Agent Graph

Nodes are agents, edges are execution dependencies. The DAG executor runs topological BFS with concurrency.

Knowledge Graph

Nodes are domain entities, edges are temporal semantic relationships. Traversal resolves current associations.

Jobs

Each graph node is a unit of work — a specific agent invocation with defined input and output variables.

Arrows + State

Edges carry type (sequential/parallel/conditional/human_gate) and optional when expression. State flows through shared vars.

13 Agent Graph Pattern (Jobs / Arrows / State)

Definition

A DAG-based execution pattern where nodes (Jobs) are agent invocations, edges (Arrows) are typed dependencies, and a shared mutable state object tracks outputs — enabling topological BFS execution with concurrent parallel batches.

Node types

worker, planner, validator, aggregator, human_gate

Edge types

sequential, parallel, conditional (with when: JS expr), human_gate

Execution

Topological BFS. Parallel batches run with Promise.all. Conditional skips cascade downstream.

Budget

maxTurns hard stops the graph. stateSchema warns on missing output keys post-execution.

pattern: graph
agentGraph:
  input:    "{{goal}}"
  output:   merged_report
  maxTurns: 20
  stateSchema:
    plan:          string
    findings_a:    string
    findings_b:    string
    merged_report: string

  nodes:
    - id: planner    type: planner    agentId: planner_agent   output: plan
    - id: research_a type: worker     agentId: researcher_a    output: findings_a
    - id: research_b type: worker     agentId: researcher_b    output: findings_b
    - id: skeptic    type: validator  agentId: critic_agent    output: critique
    - id: merger     type: aggregator agentId: synthesis_agent  output: merged_report
    - id: approve    type: human_gate                          output: approval

  edges:
    - from: planner               to: [research_a, research_b]  type: parallel
    - from: [research_a,research_b] to: skeptic                 type: sequential
    - from: skeptic               to: merger                    type: conditional
      when: "vars.critique !== 'REJECT'"
    - from: merger                to: approve                   type: human_gate

No code changes. runApp dispatches to runGraph automatically when pattern: graph is set.

14 Knowledge Graph (GraphStore)

Definition

A domain entity graph built on top of the ContextTree, where nodes represent typed domain objects and edges represent temporal semantic relationships. Graph traversal always resolves the current (open) edge for any association.

graphStore:
  nodes:
    - id: patient_jones  type: Patient  data: {name: "Jones", dob: "1965-04-12"}
    - id: room_101       type: Room     data: {number: "101",  ward: "General"}
    - id: room_icu2      type: Room     data: {number: "ICU-2", ward: "ICU"}
    - id: dr_chen        type: Doctor   data: {name: "Chen", specialty: "Cardiology"}

  edges:
    # Historical closed edge (validUntil set)
    - from: patient_jones  label: assigned_to_room  to: room_101
      validFrom: "2026-01-01"  validUntil: "2026-08-01"
    # Current open edge (no validUntil = current)
    - from: patient_jones  label: assigned_to_room  to: room_icu2
      validFrom: "2026-08-01"
    - from: patient_jones  label: assigned_to_doctor to: dr_chen

Traversing "patient_jones→assigned_to_room" returns {number: "ICU-2", ward: "ICU"} — only the open (current) edge is returned.

15 GraphContext Field Type

Definition

A context field type that resolves its value by traversing the Knowledge Graph at assembly time, using a path expression template that interpolates runtime vars to determine the start node and path.

# templates/context/doctor.context.yml
fields:
  currentPatientRoom:
    type: GraphContext
    traverse: "{{patientId}}→assigned_to_room"   # vars interpolated at runtime
    ttl: 120
    requirement: OPTIONAL
  supervisingPhysician:
    type: GraphContext
    traverse: "{{patientId}}→assigned_to_doctor→managed_by"
    ttl: 600

If vars.patientId = "patient_jones", the framework traverses the graph and injects the result as a JSON string. No TypeScript changes required to add new traversals.

16 RAG (Retrieval-Augmented Generation)

Definition

Augments an agent's prompt with the top-K most semantically relevant documents from a named retrieval store, keeping long-term knowledge outside the context window until needed.

retrievalStores:
  - id:   drug_database
    type: local_files
    dir:  knowledge/drugs         # relative to config directory

agents:
  - id: pharmacist
    retrieval:
      store: drug_database
      topK:  5                    # 5 most relevant monographs injected

17 Tools & ReAct Loop

Definition

The ReAct (Reason + Act) loop lets an agent iteratively call tools and observe results, cycling through Thought → Action → Observation until it produces a final answer or maxToolTurns is reached.

ℹ Least-privilege design

A tool not listed in agents[].tools is never sent to that agent's model — there is no way for it to be invoked, regardless of what the model requests.

tools:
  - id:   drug_calc
    type: calculator
    description: "Compute drug dosages given weight and concentration"
  - id:   formulary_api
    type: http_get
    description: "Check drug formulary status"
    allowedDomains: [formulary.hospital.internal]

agents:
  - id: pharmacist
    tools: [drug_calc, formulary_api]  # explicit opt-in
    maxToolTurns: 4

18 Output Validation & Self-Correction

Definition

Each agent can declare a validation policy that gates its output before returning upstream. On failure the agent retries up to maxRetries times with feedback injected into the next attempt.

agents:
  - id: doctor
    validate:
      type:       rule
      rule:       "output.includes('APPROVED') || output.includes('REJECTED')"
      maxRetries: 2
      onFail:     warn      # log and continue after retries
  - id: report_writer
    validate:
      type:     llm
      criteria: "Report must include patient name, diagnosis, and treatment plan"
      maxRetries: 1
      onFail:   fail        # throw after retries exhausted

19 Human-in-the-Loop

Definition

A human_gate node type in the Agent Graph that suspends execution and prompts a human for input before proceeding. The response is stored as a named var available to downstream nodes.

nodes:
  - id: approve
    type:   human_gate
    input:  "Please review the merged report. Type APPROVED or REJECTED:"
    output: human_approval

edges:
  - from: merger  to: approve  type: human_gate

20 Checkpoint & Resume

Definition

The framework periodically snapshots RunContext.vars and token usage to a checkpoint file. A subsequent run can resume from that snapshot, skipping completed steps.

# Start with checkpointing:
node dist/index.js configs/research.yaml \
  --checkpoint run-state.json

# Resume after interruption:
node dist/index.js configs/research.yaml \
  --resume    run-state.json \
  --checkpoint run-state.json

21 Observability & Tracing

Definition

A structured logging layer emitting step-level events — agent start, tool call, tool result, output, validation, token usage — to a caller-supplied log function, enabling any downstream observability backend.

// Plug in your own logger — no config change needed:
await runApp(config, baseDir, (msg) => {
  myOtelSpan.addEvent(msg);
  console.log(`[${new Date().toISOString()}] ${msg}`);
});

22 Budget Management & Safety Caps

Definition

Every looping construct carries both a turn budget (maxTurns) and an optional token budget (tokenBudget), ensuring no runaway execution can exhaust API quota or incur unbounded cost.

supervisorConfig:
  maxTurns:    10
  tokenBudget: 80000

workflow:
  loop:
    until:         "vars.review.includes('APPROVED')"
    maxIterations: 5
    tokenBudget:   30000
    onExhaustion:  fail        # throw instead of silently continuing
    statusVar:     loop_outcome # "approved" or "ITERATIONS_EXCEEDED"

agents:
  - id: pharmacist
    maxToolTurns: 4            # per-agent ReAct cap, independent of pattern cap

23 Typed Handoffs

Definition

Every data exchange between agents flows through RunContext.vars as named strings. In Plan-Execute, the planner's output is Zod-validated against the step schema and checked against the executorAgents allow-list before any step executes.

⚠ Prompt injection defense

Even if a planner LLM outputs a step referencing system_shell_agent, schema validation rejects it if that id is not in executorAgents. The allow-list is declared at deploy time, not evaluated at runtime.

planExecute:
  planner:        orchestrator
  # Only these IDs may appear in the planner's emitted step list:
  executorAgents: [web_searcher, summarizer, formatter]
  maxSteps: 8
